# Clash of Critters

Game module for Clash of Critters (`com.farlightgames.pgame.gp.vn`, base resolution 1080x1920). Code in `main.py` (commands) and the battle modules below, settings in `settings.py`, template images in `templates/`, tatari data in `tatari_db/` and `tatari_formations/`.

## Command Categories

| Category | Commands |
| --- | --- |
| Battle | `auto_battle` (Tự Động Chiến Đấu) |
| Events | `artifact_adventure` (Phiêu Lưu Cổ Vật), `artifact_adventure_limited` (Phiêu Lưu Cổ Vật Giới Hạn), `zobo_hunt` (Săn Bắn Zobo), `fishing_contest` (Cuộc Thi Câu Cá) |
| Chế Độ | `badge_dojo` (Võ Đường Huy Hiệu) |

## Auto Battle (Battle category)

`auto_battle` runs `AutoBattleMixin._run_auto_battle()` (`auto_battle.py`): a loop of `_auto_battle_step()` that reads the screen and acts. `ClashOfCritters` inherits `AutoBattleMixin` -> `DeployMixin` -> `Game`; the game supplies `_tap_common_button()`.

- Screens (templates in `auto_battle.py`): camp (`hub_battle_button`) -> stage map (`stage_map_marker`, then a fixed tap on the big yellow start button at (540, 1690): its label changes) -> preparation (`quick_deploy_button`) -> fight (`fight_button` "Chiến Đấu", or `auto_fight_button` "Tự Động Chiến Đấu" which the same button shows on later stages) -> defeat (`defeat_title`, then `retry_button` "Thử Lại", which goes back to the preparation screen) or victory (`victory_title`, then `continue_button` "Tiếp Tục", which goes back to the stage map and so on to the next stage).
- Preparation screen: the stage ("15-50") is read by OCR from `battle_layout.STAGE_LABEL_BOX`. Each stage gets a **plan** of steps (`_plan_for`): a normal stage is `[Quick Deploy, formation 1, formation 2, ...]`, a **boss stage** (number divisible by 10) is `[formation 1, formation 2, ...]`; no formation file -> `[Quick Deploy]`. Every preparation screen that starts a fight counts as one fight of the current step; after `auto_battle.max_formation_attempts` fights the next step starts, and when the last step is used up the auto battle stops. **A retry of the same step never deploys again** (only Chiến Đấu is pressed; a formation step is deployed again only if the "Đã triển khai" counter shows 0); a new step deploys (Quick Deploy button or the formation). A win clears the plan, so the next visit of that stage starts over. An unreadable stage -> Quick Deploy, outside the plan, and the auto battle stops after more than `max_formation_attempts` lost visits of it. The "Báo Cáo" icon (`prep_report_icon`) only feeds that unreadable-stage counter. Optional `auto_battle.keep_formation_after_win` (off by default): after a win with a formation (deployed or kept) the next normal stages keep the field as it is (these fights are not part of any plan), until a boss (its plan starts) or a loss (the plan of the stage starts at its first step); the field counts as kept only if the counter still shows units. Kept boss formations lost a normal stage in a live run, hence off.
- `auto_battle.max_formation_attempts` (default 3) caps the fights per step (Quick Deploy and each formation); `idle_limit_seconds` stops the loop after a long time without a known screen. The loop also stops when one known screen is seen poll after poll (`idle_limit_seconds / poll_interval_seconds` times).
- Pinball reward upgrade screen (can open after a boss stage): `_close_pinball_reward_screen()` in the auto battle loop, after the common buttons. It needs the gem icon of the reward cards (`pinball_reward_gem.png`) AND the X of the bottom bar (`pinball_reward_close.png`), then taps the X. Before the X, a card with the "Đã Mở Khóa!" banner (`pinball_reward_unlocked.png`) is tapped; that opens a popup whose "Xác Nhận" button (`pinball_reward_confirm.png`) is tapped only together with the popup title (`pinball_reward_unlocked_title.png`). The X alone is never tapped: the same bottom bar shows on the defeat and stage map screens. Not used by the Events commands.
- Formations: `tatari_formations/<chapter>/<chapter>-<stage>.json` holds `formations[]` (`source`, `level`, `units`), tried in file order; `formation.py` `load_formations` skips a malformed formation and follows `shared_with` only when `formations` is empty. Tatari data: `tatari_db/` (wiki sprites, `tatari_db.json`, `tatari_db.py`). Both folders are bundled (`tauri.bundle.templates.json`) and must be committed for CI builds.
- Deploying (`deploy.py`): clear the field (button at (1000, 880)), then for each element of the formation: filter the tray by element, scan it to its end, walk back to its start dragging the wanted cards (`deployment_plan.py` picks the owned evolution: exact, then same tatari with the nearest tier, higher first). Every drag is checked against the "Đã triển khai: n/15" counter and repeated once. `_deploy_formation` returns `DeployResult(count, needed)` (`needed` = cells with an owned tatari): while the counter is below `needed` it tries the units that failed again for up to `_FILL_ATTEMPTS` (5) rounds without clearing the field. `auto_battle._deploy_current_step` drops an incomplete formation for the next step of the plan (fresh fight count) and stops with an error log when none is left; a formation is never fought with a short field. **Unrecognized tray cards block a formation**: they look like tatari the player lacks, so after the first pass of `_deploy_formation`, if some units are absent and the recognizer has saved crops waiting (`waiting_count() > 0`), `_await_card_teaching()` logs "Có N thẻ chưa nhận ra..." with `extra={"open_card_teaching": True}` and polls the folder every second for at most `auto_battle.card_teaching_wait_seconds` (default 180, a new setting field only appears after the profile settings are reset or edited). `TauriQueueHandler` (`__main__.py`) turns that flag into the event `formation-viewer:open-cards`; the main window (`(app)/+layout.svelte`) opens the formation viewer on the cards tab (`openFormationViewer(profile, "cards")`; an open viewer switches tab through `formation-viewer:show-cards`). When no crop is left (the user taught them, which deletes the crops) the absent units are scanned and placed in a second pass without clearing the field; on timeout `DeployResult.blocked` is True (`complete` False) and `_deploy_current_step` moves on to the next formation, or stops when it was the last. The wait waits for every crop in the folder, not only those of this formation. The event and the UI need a full app build, a patch zip carries only the Python part. The wait for the tray to stop gliding after a swipe polls every `auto_battle.tray_settle_poll_seconds` (default 0.5; a new setting field only appears after the profile settings are reset or edited).
- **Drags from the tray must be steep** (|dx| <= 0.5 |dy|): a sideways drag scrolls the tray instead. `battle_layout.plan_drag` goes through a free intermediate cell and then moves the unit inside the field (checked by the target cell changing). The tray keeps gliding after a swipe: wait with `_wait_tray_stable()` before reading it, and find cards by the gaps between them (`find_card_lefts`), not by fixed slots.
- Card recognition (`card_recognition.py`): the card's element from its icon colour; then a template from the player's own earlier cards (`CardTemplateStore`, PNGs in `<app config dir>/clash_of_critters_cards/<element>/<evolution_id>.png`; delete the folder to forget them); only for an unknown card the wiki sprites are matched (outline score + colour score, glitter twin by colour). Deployed cards (dimmed with a green check) are skipped. On a template miss the store re-reads an element folder whose files (names or modification times) changed, so templates written by the formation viewer reach a running auto battle. A card the wiki matching cannot recognize either (evolved cards often fail: the art is zoomed and cropped) is saved once to `<app config dir>/clash_of_critters_unrecognized/` (a crop whose art matches a saved one at 0.8 is not saved again), and `_deploy_formation` logs how many wait.
- Geometry constants (field cells, tray slots, boxes) are measured on 1080x1920 captures kept in `docs/superpowers/specs/assets/` and `tests/games/clash_of_critters/data/`.
- **`Point` equality is always true in this repo** (a dataclass without fields): compare `(p.x, p.y)` in code and in tests.
- Formation viewer: a button left of the eye button on the "Tự Động Chiến Đấu" card (`TaskCard.svelte`) opens a second Tauri window (label `formation-viewer`, route `/formation-viewer`, one window only) with the formations of a stage and their exact tiers. The window calls the PyTauri command `get_formation_view` (`__main__.py`), which runs `formation_view.load_formation_view()`: a typed stage ("15-50", en dashes accepted) needs no device; otherwise one screenshot is taken and the stage is read by OCR from the top-centre label (`VIEW_STAGE_BOX`; visible on the preparation and fight screens only, so camp, victory, defeat and the stage map answer `stage_unreadable`). Statuses: `ok`, `no_device`, `stage_unreadable`, `stage_invalid`, `no_formation`. It only takes a screenshot and never sends input, so it is safe while the auto battle runs. Sprites travel as 96 px base64 data URIs (CSP `img-src 'self' data:`). Second tab "Thẻ chưa nhận ra (N)" (`UnrecognizedCards.svelte`): the saved crops of unrecognized cards; the user picks the evolution from the wiki sprites of the card's element and saves. Commands `get_unrecognized_cards` and `teach_card` (`__main__.py`) run `card_teaching.load_waiting_cards()` / `teach_card()`: the crop becomes the template of that evolution, and it and every other crop of the same card are deleted; an id not in `tatari_db`, of another element, or a crop id not listed returns a status, never an exception. **A patch zip carries only the Python part**: the button, the window, its tabs, the CSP and the capabilities need a full app build.

## Võ Đường Huy Hiệu (Chế Độ category)

`badge_dojo` runs `BadgeDojoMixin._badge_dojo()` (`badge_dojo.py`; `ClashOfCritters` inherits `BadgeDojoMixin` -> `AutoBattleMixin` -> `DeployMixin`). Design and measurements: `docs/superpowers/specs/2026-11-24-coc-badge-dojo-design.md`, captures `docs/superpowers/specs/assets/dojo_*.png`.

- Entry: `modes_button.png` ("Chế Độ", on the camp and the pinball screen, so no `_open_pinball_screen()`), then `badge_dojo_banner.png`. Then for each element tab (water, fire, grass, rock, lightning; centres y 1720, x 125/330/540/745/955): the "Thử Thách" button must be yellow (`challenge_button_is_yellow`, mean HSV of a patch of its edge: yellow (24, 244, 253), grey (0, 0, ~130)); a grey tab is skipped. Yellow: tap "Thử Thách" (540, 1495), then `dojo_start_button.png` ("Bắt đầu", found by template: it sits under the current stage).
- Geometry: `battle_layout.DOJO_LAYOUT` (a `PrepLayout`; `DeployMixin._layout` is `BATTLE_LAYOUT` by default and `_badge_dojo` sets `DOJO_LAYOUT` for its run, restored in `finally`). The dojo field is 3 columns x 4 rows with at most 5 units (the row above is a neutral row: a drop there does not register), the tray has 5 wider columns (card ~194x232, a crop is resized to the battle card size 160x190 before recognition), no element filter (the tray holds only the element of the Võ Đường), clear button (1000, 1040), counter box (100, 1130, 630, 1210), stage label box (500, 45, 640, 110).
- Formations: `tatari_dojo/<element>/<dojo>-<stage>.json` through `formation.load_dojo_formations(root, element, StageId(dojo, stage))` (`shared_with` like "4-1 – 4-10" is followed inside the element folder). `tatari_dojo/` is bundled (`tauri.bundle.templates.json`) and must be committed. A stage reads as "4-2" = Võ Đường 4, stage 2.
- Stage loop (`_dojo_step`, verified on a live MuMu run of Võ Đường Thảo, stages 4-3 to 4-10): the preparation screen is recognised by the existing `quick_deploy_button.png` (never pressed) and the fight button by `fight_button.png`; result screens by `victory_title.png` / `defeat_title.png`. The first stage of a run builds a plan of its formations only (no Quick Deploy, no boss rule) and goes through `AutoBattleMixin._play_plan_step` (clear, deploy, fight). **After a win the game keeps the field: the next stage of the same Võ Đường is fought with it** (`_keep_field`, `_fight_with_the_kept_field`; a kept fight is not part of the plan and is recorded as formation 0); only a loss deploys the formations of the stage, `max_formation_attempts` fights each, then `dojo_defeat_back_button.png` ("Trở Về" of the defeat screen) and the next element. A win taps `dojo_continue_button.png` ("Tiếp tục" goes straight to the next preparation screen). "Thử Lại" (`dojo_retry_button.png`) returns to the preparation screen with the field kept.
- End of a tier: the win screen of **stage 9 has only a white "Trở Về"** (`dojo_victory_back_button.png`, the text matches both the one- and the two-button layout; pressed after 2 polls without "Tiếp tục") which goes back to the Võ Đường screen; the win of **stage 10 shows a green "Nhận Huy Hiệu"** (`dojo_claim_badge_button.png`). Both return `"again"`: `_play_element` goes back (`_return_to_dojo_screen`), re-checks that the "Thử Thách" button is still yellow and enters the same Võ Đường again with `resume=True` (the kept field is used), at most `MAX_REPLAYS` times. After the badge is claimed: a speech box of the master (`master_dialog_shown`, a white box across the bottom, tapped at (540, 1760), several lines), the word "Nhận" on the statue (`dojo_receive_text.png`, tap it), then the badge screen with "Tuyệt vời!" (`dojo_great_button.png`), then the Võ Đường screen; after Võ Đường 4 of the grass element all five tabs were grey (tier 5 not open).
- Screens that need no template: the "Mở Thêm Nhóm" reveal after a win (5/15, 10/15, 15/15; the button pulses so a template of its text matches one size only: `more_group_reveal_shown` finds the lime button across the bottom by colour, tapped at (540, 1710)); "Đặc Điểm Mới!" popups (`dojo_new_trait_title.png`, tap (540, 1600)). `_tap_overlay_screens` takes one screenshot per poll for the reveal and the master dialog.
- Leaving: an unreadable stage label (3 polls), a stage without a formation file, a plan that cannot be deployed, or a known screen that never changes (`_is_stuck`) leaves; the arrow of the preparation screen (85, 1800) goes back to the **camp screen** (verified); "Trở Về" of a win screen goes to the Võ Đường screen (verified); "Trở Về" of a defeat screen was not seen live. `_return_to_dojo_screen()` brings the bot back to a Võ Đường screen (`dojo_my_badges_button.png`, on every element's screen) from the camp or pinball screen, the Chế Độ screen, the stage list (its X (540, 1845)), a win or defeat screen left behind, or the badge screens above.
- The tray of a Võ Đường only holds one element, so `_play_dojo` sets `_tray_element` and `CardRecognizer.recognize(card, element=...)` skips reading the element from the icon colour (a card whose background bleeds into the icon box was read as the wrong element). A card that is still unrecognized (an evolved tatari the player never taught) blocks the formation like in auto battle: teach it in the formation viewer, or with `CardTemplateStore.save(evolution_id, crop)` when the crop's element cannot be read.
- A result screen can be seen on two polls in a row: `_dojo_result_recorded` makes sure a fight is recorded once. When all is done `format_dojo_summary` logs every fight (element, stage, formation, attempt, result), per-element totals and the skipped elements.

## Events Category Rules

- **Every command in the `Events` category must make sure the pinball screen is open first.** Camp screen shows the "Pinball" tab (`pinball_tab.png`); pinball screen shows the "Camp" tab (`camp_tab.png`; the crop excludes the optional pinball-ball bubble so it matches with or without it). Already on pinball: stay; on camp: tap "Pinball".
- Use the shared helper `_open_pinball_screen()` as the first step after `open_eyes()`. Do not re-implement it per command.
- A new Events command must call `_open_pinball_screen()` first.

Example:

```python
@register_command(gui=GUIMetadata(label="...", category="Events"))
def my_event(self) -> None:
    self.open_eyes(device_streaming=False)
    self._open_pinball_screen()
    ...
```

## Templates

- `templates/pinball_tab.png` is the crop of the "Pinball" tab (bottom-right of the main screen, icon + label, x 880-1060, y 1745-1900 of 1080x1920). Also required: `camp_tab.png` (crop of the "Camp" tab, x 900-1050, y 1790-1900, on the pinball screen).
- The whole `templates/` folder is bundled via `src-tauri/tauri.bundle.templates.json`; no per-file registration is needed.
- `templates/artifact_adventure_icon.png` is the black-cat card on the pinball screen (right side). It is cropped to the ear/eye area (x 930-990, y 725-772) on purpose: the torch count bubble, the number in the middle and the "ends in N days" label are dynamic and must stay out of the crop.
- `templates/zobo_hunt_icon.png` is the golden-trophy card of the Zobo Hunt event (Săn Bắn Zobo) on the pinball screen, cropped to the Zobo face on the trophy (x 948-1000, y 508-555 of a real 1080x1920 screenshot; a downscaled crop does not match); the coin bubble, the number and the "ends in N days" label are dynamic and excluded. `zobo_hunt_start_button.png` is the "Bắt Đầu Ngay" text (x 430-810, y 1795-1865). `zobo_hunt` opens the event (skipped if the start button is already shown), waits 20s so the user can adjust settings, then presses "Bắt Đầu Ngay". In the arena (`zobo_hunt_arena_close.png`, the bottom "X", x 495-585, y 1805-1890) it loops: press each buff whose label is visible (`zobo_hunt_rage_button.png` "Cuồng Nộ" x 900-1050 y 1460-1502, `zobo_hunt_target_lock_button.png` "Khóa Mục Tiêu" x 898-1050 y 1672-1710; while a buff runs (~20s) its label becomes a countdown, so a visible label means ready), then `hold()` the arena centre for 3s to shoot. Stops when the arena is not seen for 60s. A red speech bubble can cover the Cuồng Nộ label briefly; the next loop retries.
- `templates/fishing_contest_icon.png` is the fish card of the Fishing Contest event (Cuộc Thi Câu Cá) on the pinball screen, cropped to the fish head and eye (x 910-968, y 720-772 of a real 1080x1920 screenshot); the rod count bubble, the number and the "ends in N days" label are dynamic and excluded. `fishing_contest_title.png` is the "Cuộc Thi Câu Cá" title (x 285-800, y 30-105): if it is shown the pinball step is skipped. The round fishing button (centre (540, 1580)) changes its rod picture, rod count and "x1" badge, so `fishing_button_state()` reads its state from the mean HSV colour of the left edge of the circle (x 415-435, y 1560-1600): green = cast (tap), grey = waiting, purple = bite (tap to reel in; it stays purple for a few polls, every tap is fine), anything else = a popup dims it. Popups are searched only while the state is unknown: the reward popup (`artifact_adventure_claim_button.png` "Nhận Ngay") and the catch result screen (`fishing_contest_result.png`, the "người chơi trên" text, x 495-915, y 1322-1378; without "máy" because "Đánh bại 100,00%" on a new server record wraps "máy chủ!" to the next line; the "Kỷ lục cá nhân/máy chủ mới!" banner screens are this same screen), which stays until a tap on the dimmed top area (540, 250); a tap on the fish does not close it. Stops when green stays 10s after a cast (out of rods) or no known state for 60s. Tension bar (after some bites, while the button is purple): a red bobber runs back and forth on its own (~300 px/s, x ~380-800) over a bar (band x 270-850, y 1230-1340) with a yellow zone; tap the button while the bobber is in the zone. Each hit shrinks and moves the zone, so several hits are needed. `read_tension_bar()` returns the bobber x and the yellow extent; the "Ngay! Kéo cần đi!" bite timer bar is yellow too but has no bobber, so it reads as None. `_play_tension_bar()` reads the zone only while the bobber is more than 40 px outside of it (the bobber hides the yellow under it), forgets it after every tap so the shrunk zone is read again, and times every tap to land on the zone centre. The bobber moves on a triangle wave (x 308-806, ~352 px/s, half period ~1.41 s, measured on MuMu; the old values 380-800 and 300 px/s were wrong). The H264 stream is bursty (stalls of ~0.5 s, then catch-up; frames up to ~0.2-0.4 s stale), so a speed measured from frame arrival times is useless (it read 0 to 1800 px/s). `HeadingTracker` gives the direction from runs of steady frames (it restarts at every jump >30 px and at every turn, and gives the direction back to the whole run, also the first, freshest, frame after a jump); `BobberClock` learns the phase of the wave in wall-clock time as a lower envelope over the frames (a fresher frame moves it earlier, it creeps later by 0.02 s per s, a frame >0.5 s off is ignored); `plan_tap()` waits until the model puts the bobber on the zone centre `fishing_contest.tap_lead_seconds` later (default 0.2 s = delay of the freshest frame + delay of the tap, a guess: it can only be measured by real taps, so every tap logs the bobber, the zone, the lead and where the model puts the bobber when the tap lands; each missed tap costs the player game time, so tune it with 2-3 casts at most). After a tap the zone is not read for lead + 0.3 s (the shrunk zone shows only after the tap landed and a possibly stale frame came in), so a held frame cannot tap twice. The first ~0.5 s of a bar may be off until a fresh frame arrives. The setting field appears in an existing profile only after its settings are reset or edited, and a patch zip carries only the Python part. It needs fresh frames many times a second, so `fishing_contest` runs with device streaming (~25-30 fps); with streaming disabled in the ADB settings it falls back to screencap (~2 fps) and will mostly miss.
- Artifact Adventure templates: `artifact_adventure_start_button.png` (text of "Bắt Đầu Phiêu Lưu!"; the "1x" badge above is dynamic), `artifact_adventure_advance_button.png` ("Tiến Lên" text only; the torch icon changes with the torch type and the torch count below is dynamic, so both are excluded), `artifact_adventure_tap_to_continue.png` ("Chạm điểm bất kì để tiếp tục"). `artifact_adventure` loops over these three screens (plus the fight/retreat, reward and claim screens below); if none is seen for 60s it stops.
- Claim popup (`artifact_adventure_claim_button.png`, "Nhận Ngay" text only, x 385-700, y 1735-1810): the "Bàn Tay Vàng" popup can appear mid-adventure; the loop taps the button to continue.
- Common buttons (any screen, any command): `open_all_button.png` ("Mở Tất Cả" text only, x 648-945, y 1672-1752; the "5/30" badge of the neighbouring "Mở thêm nhóm" button is dynamic) and `ok_button.png` ("OK" text only, x 488-598, y 1738-1802, on the "Phần Thưởng!" screen). `more_group_button.png` ("Mở thêm nhóm" text only, x 330-755, y 1672-1752, when it is the only button on screen; the "5/6" badge above is dynamic). Whenever one is seen it is tapped: the battle loop via `_tap_common_button()` before its normal checks, and the Artifact Adventure loop via `_COMMON_BUTTONS`. Add new always-tap buttons to `_COMMON_BUTTONS` / `_COMMON_BUTTON_LOG`.
- Fight-or-retreat choice (`artifact_adventure_retreat_button.png` / `_fight_button.png`, icon + title only): the win rate is read by RapidOCR from the line under the Fight card and all `N%` values are summed (base + bonus). Fight if the sum is >= `artifact_adventure.min_win_rate_percent` (default 80), otherwise retreat; an unreadable rate also retreats. After a retreat the reward screen is closed with `artifact_adventure_accept_button.png` ("Chấp Nhận").
- `artifact_adventure_limited` shares all logic with `artifact_adventure` via `_artifact_adventure(max_advances)`; it counts "Tiến Lên" presses and stops at the next stage / new-adventure screen once `artifact_adventure.limited_advance_count` is reached (pending tap-to-continue, fight/retreat and reward screens are still handled first).

## Packaging a Patch Zip for the Installed App

When the user asks for a zip of this game to copy into their installed AdbAutoPlayer (`%LOCALAPPDATA%\AdbAutoPlayer`), build it with the layout below so the user can extract it straight over the install root.

- Python code goes to `Lib/site-packages/adb_auto_player/games/clash_of_critters/`: every `.py` file of the folder (`__init__.py`, `main.py`, `settings.py`, `auto_battle.py`, `deploy.py`, `battle_layout.py`, `card_recognition.py`, `deployment_plan.py`, `formation.py`, `formation_view.py`, `card_teaching.py`, `tatari_db.py`, `badge_dojo.py`).
- The data folders `tatari_db/`, `tatari_formations/` and `tatari_dojo/` go to `games/clash_of_critters/` next to `templates/`.
- Template images go to `games/clash_of_critters/templates/` (the install root, where Tauri bundles resources, per `src-tauri/tauri.bundle.templates.json`). This is the folder the app reads templates from.
- Never include `__pycache__/`, `README.md`, `CLAUDE.md` or tests.
- Default settings (`src-tauri/settings/ClashOfCritters.toml`) are compiled into the app and are not in the install folder; mention to the user that a new setting field only appears after the profile settings are reset or edited, and do not add the toml to the zip unless asked.
- Output: `clash_of_critters_patch_v<version>.zip` two levels above the repo (`N:/00_PersonalProject/AdbAuto-CoC/`) by default, or wherever the user names. Print the zip path and its file count when done.
- Ask the user for the version (`X.Y.Z`) before building; never guess it.

Build it with the script (packages files from git `HEAD`, so commit first) or the `coc-patch` skill, which also drafts the release note:

```bash
python scripts/build_coc_patch.py <version> [--ref <git-ref>] [--out <dir>]
```

The user extracts the zip into `%LOCALAPPDATA%\AdbAutoPlayer` and overwrites existing files, then restarts the app.
